# OriBrink 数据平台需求文档（多源接入与特征解耦）

- 文档版本：v1.0
- 日期：2026-02-10
- 适用范围：数据接入层、标准化层、特征层（L0/L1/L2）
- 目标：支持异构数据源快速接入与特征体系持续演进

## 1. 背景与问题定义

当前项目的数据来源可能长期处于动态变化状态：
1. 离线数据：购买的历史 CSV/Parquet。
2. 历史 API：第三方历史行情接口。
3. 实时 API：实时行情/盘口/事件接口。
4. 非标准采集：安卓模拟器采集、爬虫抓取、半结构化文本解析。

核心挑战：
1. 数据结构异构，字段口径不一致，时间粒度不同。
2. L0/L1/L2 指标定义尚未收敛，后续会频繁变更。
3. 若策略直接耦合具体数据源与字段，系统会快速失控。

## 2. 总体目标

1. 建立统一的“多源接入协议”，新增数据源不改主流程。
2. 建立标准数据模型（Canonical Schema），屏蔽来源差异。
3. 建立解耦特征引擎，使 L0/L1/L2 可版本化演进。
4. 建立可追溯链路，任意信号可回放到原始数据与计算版本。

## 3. 架构要求（解耦分层）

采用 5 层解耦架构：

1. Source Layer（数据源层）
- 各类数据源适配器：CSV/API/实时流/爬虫/模拟器。
- 仅负责获取数据，不参与业务计算。

2. Ingestion Layer（接入层）
- 统一接入协议与任务调度。
- 输出原始数据包与元数据（来源、抓取时间、批次号）。

3. Canonical Layer（标准化层）
- 做字段映射、时间对齐、代码规范化、去重。
- 输出标准模型，供所有下游复用。

4. Feature Layer（特征层）
- 通过特征注册机制生成 L0/L1/L2 及派生指标。
- 支持配置驱动，不把指标逻辑写死在策略里。

5. Consumer Layer（消费层）
- 策略、回测、盘前选股、盘中提醒、复盘系统。
- 只消费标准层/特征层数据，不直接依赖原始源。

## 4. 通用接口需求（核心）

### 4.1 Source Adapter 接口

目标：屏蔽各类来源差异。

建议接口：
- `source_id()`：返回唯一数据源标识。
- `capabilities()`：返回支持的数据类型与时间粒度。
- `fetch(request)`：拉取指定范围数据。
- `health_check()`：检测源可用性。

输入示例：
- 标的范围、时间范围、频率、字段列表、增量游标。

输出示例：
- 原始记录列表 + source metadata（抓取时刻、请求参数哈希、批次号）。

### 4.2 Normalizer 接口

目标：将原始数据转为标准模型。

建议接口：
- `normalize(raw_batch) -> canonical_batch`
- `schema_version()`：当前标准模型版本。

要求：
1. 统一字段命名（symbol, ts, open, high, low, close, volume...）。
2. 明确时区与交易日规则。
3. 记录字段映射与转换日志。

### 4.3 Feature Provider 接口

目标：解耦指标演进与策略逻辑。

建议接口：
- `feature_id()`：特征唯一标识。
- `depends_on()`：声明依赖字段/上游特征。
- `compute(context) -> feature_frame`
- `feature_version()`：特征版本号。

要求：
1. 支持新增/替换/废弃，不影响既有策略运行。
2. 支持窗口类计算（如 t0-80 到 t0）。
3. 支持按市场状态分支计算（震荡/主升/退潮）。

### 4.4 Snapshot & Lineage 接口

目标：保证可回放和可审计。

建议接口：
- `publish_snapshot(data_version, feature_version)`
- `get_snapshot(trade_date)`
- `trace_lineage(signal_id)`

要求：
1. 任何信号结果都能定位到：数据版本、特征版本、策略版本。
2. 支持跨环境复现（研究环境 vs 生产环境）。

## 5. 数据治理与质量要求

必须建立数据质量规则：
1. 完整性：关键字段缺失率阈值。
2. 唯一性：主键重复率阈值。
3. 时序性：时间戳连续性与乱序检测。
4. 合法性：价格/成交量范围校验。
5. 一致性：多源同字段口径差异监控。

质量输出：
- 每日质量报告（按数据源、按字段、按任务）。
- 质量评分进入策略使用门槛（低质量数据可降权或隔离）。

## 6. 扩展性要求

1. 新增数据源
- 仅新增 `adapter` 与映射配置，不修改策略服务。

2. 新增特征
- 仅新增 `feature provider` 并注册，不改策略主流程。

3. 新增消费场景
- 通过标准层/特征层 API 直接消费，不依赖原始源。

4. 多环境支持
- 本地、回测、生产共享同一套接口契约。

## 7. 非功能需求

1. 可用性
- 关键接入任务成功率 >= 98%。

2. 时效性
- 盘前批处理在窗口内完成。
- 盘中准实时任务延迟可观测。

3. 可维护性
- 各层模块具备单元测试与契约测试。

4. 可观测性
- 指标：任务耗时、失败率、数据质量、源健康状态。

5. 安全性
- 数据源凭据集中管理，不硬编码，不入库明文。

## 8. 验收标准（可量化）

1. 接入效率
- 新增一个历史数据源接入 <= 2 人日。

2. 稳定性
- 连续 20 个交易日接入任务成功率 >= 98%。

3. 解耦有效性
- 变更任一数据源实现，不影响策略接口与回测接口。

4. 可回放
- 任一交易日可完成“原始 -> 标准 -> 特征 -> 信号”链路重放。

5. 特征演进
- 新增 1 个 L2 特征不需要改已有策略代码（仅配置或注册）。

## 9. 里程碑建议（对应当前 12 周计划）

1. 里程碑 A（Week 1-4）
- 完成统一接入接口、标准化模型、L0 基础特征链路。

2. 里程碑 B（Week 5-8）
- 完成 L1/L2 特征注册体系、版本管理、质量报表。

3. 里程碑 C（Week 9-12）
- 完成准实时接入与提醒链路、可回放与血缘查询。

## 10. 建议目录（与当前仓库对齐）

```text
services/
  data_service/
    adapters/           # csv/api/realtime/crawler/emulator
    ingestion/          # 拉取任务与游标管理
    normalization/      # canonical schema 转换
    quality/            # 质量校验规则与报告
  feature_service/
    registry/           # 特征注册表
    providers/          # L0/L1/L2 特征实现
    snapshots/          # 版本发布与快照管理
  strategy_service/
    consumers/          # 只消费标准层/特征层
shared/
  schemas/              # canonical schema + feature schema
  lineage/              # 溯源模型
```

## 11. 结论

该需求可概括为：
“以统一接口契约和分层解耦架构为核心，构建支持多源异构接入、特征持续演进、全链路可追溯的数据平台，为策略迭代和实战执行提供稳定数据基础设施。”
