# OriBrink 内部执行版 PRD（2026）

- 版本：v1.1（内部执行版）
- 日期：2026-02-09
- 目标周期：2026-01-01 ~ 2026-12-31
- 技术路线：Python + Web（FastAPI + 前端看板）

## 1. 这项目到底要做什么

一句话：
做一个“盘前量化初筛 + 人工决策把关”的交易辅助系统，不做全自动交易。

核心价值：
1. 盘前用量化把全市场快速缩到可操作的候选池。
2. 盘中把注意力集中在关键决策窗口（开盘前后、尾盘）。
3. 盘后把每次决策结构化记录，推动策略持续迭代。

年度目标（2026）：
1. 盘前稳定覆盖 >= 4000 标的，输出 20~50 支观察池。
2. 每个新策略从提出到可回测 <= 7 天。
3. 形成“盘前-盘中-盘后-周迭代”闭环并持续运行。
4. 组合风控可控（先控制回撤，再追求收益）。

## 2. 不做什么（边界）

1. 不做无人值守自动下单。
2. 不做高频、超低延迟基础设施。
3. 不做重型 NLP 舆情系统（先预留接口）。
4. 不把“固定收益率”写成系统承诺。

## 3. 你们要做的工作（工作分解）

## 3.1 工作流总览

每天：
1. 日终更新数据 -> 计算特征。
2. 次日盘前跑策略 -> 输出候选池。
3. 盘中按提醒 + 人工研判执行。
4. 盘后记录交易与失效样本。

每周：
1. 汇总样本（成功/失败/错过）。
2. 跑回测和参数扰动测试。
3. 迭代策略版本并更新上线状态。

## 3.2 四大模块（必须先做）

1. 数据模块（Data）
- 做什么：采集、清洗、标准化、存储。
- 必交付：
  - `symbol_daily`（日线）
  - `symbol_intraday`（分钟）
  - `auction_snapshot`（竞价）
  - 交易日历、复权因子、基础信息
- 完成标准：可按“日期+代码”稳定查询，缺失与异常可告警。

2. 特征与策略模块（Feature + Strategy）
- 做什么：把经验规则写成可计算信号。
- 必交付：
  - L0/L1/L2 特征表
  - 策略接口（参数化，版本化）
  - 首批策略模板（弱转强、潜龙在渊）
- 完成标准：同样输入数据必得同样信号结果。

3. 回测与评估模块（Backtest）
- 做什么：验证策略是否可用、是否稳定。
- 必交付：
  - 日频回测链路
  - A 股约束模拟（T+1、涨跌停、手续费、滑点）
  - 绩效报告（收益、回撤、胜率、盈亏比）
- 完成标准：回测结果可复现，可按策略版本追溯。

4. 盘前与复盘模块（Pre-market + Review）
- 做什么：让系统真正服务实战。
- 必交付：
  - 盘前候选池（含命中条件/风险标签）
  - 盘中提醒（条件触发）
  - 交易日志与周报
- 完成标准：形成稳定日常节奏，可持续迭代。

## 4. 系统怎么实现（可扩展架构）

目录建议：

```text
oribrink/
  services/
    data_service/         # 数据接入与清洗
    feature_service/      # L0/L1/L2 计算
    strategy_service/     # 策略执行与打分
    backtest_service/     # 回测撮合与评估
    selection_service/    # 盘前候选池生成
    review_service/       # 交易日志与复盘
    api_service/          # FastAPI 对外接口
  shared/
    schemas/              # Pydantic/SQLModel schema
    utils/                # 公共方法、交易日历、日志
  web/
    dashboard/            # 清单、提醒、复盘看板
  docs/
```

关键设计原则：
1. 分层解耦：数据、策略、回测、应用分开。
2. 插件化策略：新增策略不改主流程。
3. 版本可追溯：数据版本 + 策略版本 + 参数版本。
4. 研究生产分离：研究脚本和线上任务分开。

核心接口（先定死，后续好扩展）：
1. `DataProvider.get_bars(symbols, start, end, freq)`
2. `FeatureEngine.compute(date)`
3. `Strategy.generate_signals(date, params)`
4. `Backtester.run(strategy_version, period, config)`
5. `Selector.build_watchlist(date)`
6. `Review.log_trade(payload)`

## 5. 数据与策略实现重点

## 5.1 数据分层定义（结合你们当前思路）

L0（逐日基础行为，偏盘前服务）：
- 竞价涨幅、竞价成交量
- 全天/上午高低点及时间
- 涨停/炸板/烂板标记
- 尾盘抢筹标记
- 换手率等

L1（滚动统计，t0-80 ~ t0）：
- 涨停平均溢价
- 涨停成功率
- 次日溢价 >5% 次数
- 闷棍次数

L2（风格与股性，t0-80 ~ t0）：
- 股性评分
- 辨识度
- 反包指数
- 各风格赚钱/亏钱效应

## 5.2 策略落地规则

每个策略必须有：
1. 触发条件（硬条件）
2. 过滤条件（风险剔除）
3. 打分逻辑（优先级）
4. 失效条件（何时不做）
5. 复盘标签（便于统计）

策略文件最小结构：
- 输入：特征表 + 参数
- 输出：`symbol/date/score/tags/reason`

## 6. 开发顺序（按可落地优先）

Phase 1（2~4 周）先跑通最小闭环：
1. 完成日线 + 竞价数据入库。
2. 实现 L0 特征。
3. 上线 1 个策略（弱转强）和日频回测。
4. 每日导出盘前候选 CSV。

Phase 2（4~8 周）做可用性提升：
1. 加入 L1/L2 特征。
2. 上线第 2 个主策略（潜龙在渊）。
3. Web 看板支持候选池查询和交易日志录入。
4. 建立周报自动生成。

Phase 3（8~12 周）做稳定性与扩展：
1. 增加盘中提醒。
2. 参数扰动测试与策略健康度分级。
3. 形成策略组合管理与停用机制。

## 7. 每周执行模板（建议直接照做）

周一到周五：
1. 08:30 前：生成候选池，人工确认观察清单。
2. 交易时段：记录触发与实际操作。
3. 收盘后：补全日志，标注成功/失败/错过原因。

周六：
1. 复盘失败样本 Top N。
2. 回测本周改动。
3. 输出下周策略变更单。

周日：
1. 固化参数版本。
2. 更新策略白名单（继续/降权/停用）。

## 8. 验收口径（避免“做了很多但不确定是否有效”）

基础验收：
1. 任务成功率：盘前任务成功率 >= 98%。
2. 数据质量：核心字段完整率 >= 99.5%。
3. 研发效率：新策略接入 <= 7 天。

业务验收：
1. 候选池规模稳定在 20~50 支。
2. 人工认为“有价值提醒”比例 >= 60%。
3. 至少 2 个策略通过样本外稳定性检查。

## 10. 工程工具与标准命令（统一为 uv）

工具栈（执行层）：
1. `uv`：依赖同步、虚拟环境、命令执行统一入口。
2. `docker compose`：本地 PostgreSQL/Redis。
3. `FastAPI + Uvicorn`：API 服务。
4. `APScheduler`：定时任务。

标准命令：
1. 初始化：`bash scripts/bootstrap.sh`
2. 启动依赖：`docker compose up -d`
3. 启动 API：`uv run oribrink-api`
4. 启动调度器：`uv run oribrink-scheduler`
5. 健康检查：`curl http://localhost:8000/health`
6. 检查与测试：
- `uv run ruff check .`
- `uv run mypy services shared`
- `uv run pytest`
